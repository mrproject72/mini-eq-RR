# 2026-10-05

## The clipping pair is two same-shape buttons

`[Clip] [Fix] [Auto]` — both controls are buttons now, same width (56px), fixed
labels, and colour is the only thing that carries state:

- **Fix**: red when the curve peak is over the target and the button is live,
  plain grey otherwise.
- **Auto**: green while on, plain grey while off. It is a `ToggleButton`
  replacing a `Switch`, so the pair reads as one shape; the redundant "Auto"
  text label that sat beside it is gone.

Two things this changed that needed care:

- The resting green (`clip-safe-ok`) is gone. Green means "Auto is on" in this
  pair, and reusing it for "nothing to do here" made two different states look
  identical. Fix is grey at rest and insensitive, with `opacity: 1.0` so GTK
  does not dim it into looking missing.
- The blinking clipping alert was invisible against a permanently red Fix — both
  classes set the same fill. The blink now drops the fill to an outline, so it
  alternates outlined/solid red while Fix stays red throughout.

## Labels back, shorter preamp caption, blink follows the red state

- The caption-hiding compaction is gone. It was my answer to the row-wrap
  problem and it made the row unreadable at ordinary window sizes — every
  caption hidden below 1000px, leaving tooltips and bare controls. Grouping the
  clipping pair and shrinking the Fix button freed enough width that the
  captions fit, so the rule (and its two threshold constants) is deleted.
- Caption `Preamp` -> `Pre`: it sits in front of a spin button that is already
  ~165px wide. Full name stays in the tooltip.
- Peak readout 11 -> 12 characters, because "-100.0 dBFS" is 12 and the label
  ellipsised exactly when the peak was loudest.
- The clipping blink is now triggered by the Fix button's own red class instead
  of a separately computed level condition. The two were computed from
  different things (live peak over target vs. curve peak needing a manual fix)
  and disagreed, so the button could be red and still, or blink while grey. Red
  now means red-and-blinking. The dead shared `headroom_warning` flag is
  removed with it.

Measured at the minimum window width: row is one line (40px), 691px allocated,
all four cells present (Smooth 121, Pre 136, status 110, Clip 155). 120 tests,
fmt, clippy clean.

## Exit no longer takes the audio with it

See `docs/BUGS.md` for the full account. Two fixes:

- `src/exit_guard.rs`: SIGTERM/SIGINT are caught into an atomic flag, and the
  33 ms update loop turns that into a clean quit. `kill`, `pkill` and the
  session manager stopping a user unit all send SIGTERM, whose default action
  killed the process before any cleanup ran.
- The exit restore now *names* the destination sink (`unroute_all_to`) instead
  of only clearing `target.node`/`target.object` and leaving the choice to
  WirePlumber. Destination is the sink the EQ was feeding, falling back to the
  system default.

`libc` added as a direct dependency for the two signal numbers (it was already
in the tree transitively).

Verified with a real routed stream on both paths: SIGTERM and D-Bus Quit both
restore Waterfox and speech-dispatcher to the ALC897 hardware, logged stream by
stream. 121 tests, fmt, clippy clean.

## Exit hand-off: one roundtrip instead of one per stream

The gap when closing the window is inherent — the streams are moved off the EQ's
virtual sink and WirePlumber re-links each one — but the app was adding to it:
`set_stream_target` roundtrips per stream, so five players meant five serialised
PipeWire syncs before the first stream was told where to go.
`unroute_all_to` now queues all the target writes and syncs once.

Verified: exit still restores 3 streams to the ALC897 hardware in one pass.
Whether the remaining gap is audibly shorter needs an ear — nothing here can
measure it.

## "Save preset" now saves the curve on screen

`current_bands` was only updated when a preset was *loaded*, never from
subsequent edits, so the Save button wrote the `default_bands()` flat curve it
was constructed with. The panel now takes a `current_state_callback` — wired to
the same fader + preamp source the state signature reads — and uses it when
saving. The panel's copy of "current" is refreshed from what was written, so the
chip reads *saved* rather than *modified*, and save failures are logged instead
of silently dropped. Export and the APO/AutoEq import paths were never affected:
they carry their own bands.

121 tests, fmt, clippy clean.

## Turning the System EQ switch off is faithful now (upstream's model)

Checked the Python upstream, and the port was doing something different on the
way back:

- Upstream records each stream's `target.node` / `target.object` — values *and
  metadata types* — before routing it into the EQ, and restores exactly that on
  disable (`PipeWireStreamRouter.restore_output_streams`).
- The port cleared both properties, leaving the destination to WirePlumber,
  which re-resolves the stream's target from scratch. That re-resolve is the
  ~1s of silence.

Now: the metadata `property` listener (already bound for
`default.audio.sink`) feeds a per-subject target cache, originals are recorded
at route time, and `unroute_all` writes them back verbatim in one batched sync.
Streams this process never routed fall back to the EQ's output sink.

`unroute_all` is also idempotent now — one toggle used to run it twice, via both
the UI switch and D-Bus, and the second pass rewrote targets that were already
right; it now reads the streams' targets to see whether anything is still on the
EQ and returns early.

Verified: 3 streams restored to their own targets, second call a no-op, `wpctl`
shows them back on the ALC897 hardware. 121 tests, fmt, clippy clean.

Not changed: upstream refuses to route a stream that already has a foreign
target; the port routes everything and restores it faithfully afterwards.

## Routing now touches only the streams upstream would

Upstream's four filters are ported verbatim: internal/blocklisted streams
(our client, the chain output, `media.role` of event/Notification, and the
`GNOME Shell`/`Mutter`/`gsd-media-keys`/`libcanberra`/`speech-dispatcher*`
names), streams with a foreign `target.object`, and `node.dont-move` streams.
`list_stream_nodes` now collects `node.name`, `application.name`, `media.role`
and `node.dont-move`, which the port never read before. The restore uses the same
filter, so a stream we refuse to route is never written to either.

Two latent defects surfaced while verifying:

- `stream_target` unpacked the cache's `(type, value)` the wrong way round, so
  every stream's target read as `"Spa:Id"`. That made the new filter reject
  everything, and the earlier "faithful restore" had been writing types into the
  value slot.
- A stale `target.object` naming a sink that no longer exists (left by the above)
  blocked routing permanently. Treated as no explicit target.

Verified: Waterfox and fooyin route through the EQ, speech-dispatcher stays on
the hardware, and switching off restores both to their own targets.
`MINI_EQ_DEBUG_ROUTING=1` dumps the filter's inputs and verdicts.
121 tests, fmt, clippy clean.

## Per-output presets actually switch now

The storage existed and the behaviour did not. `core.rs` gains the reader
(`output_preset_for_sink`, keyed by sink identity via
`output_preset_key_for_sink`), and `window.rs` gains
`apply_output_preset_for_sink`, called after a successful output switch. It
mirrors upstream's `output_preset_target_transition`: the last identity is
remembered so only a real change loads a preset. The Link button now writes the
sink's node name instead of the literal `"default"`, which is what it was
writing before.

The default-sink watcher stays out of it: the filter chain does not follow the
system default, so there is no change to switch on. Noted in the helper.

Tested at unit level (own link wins, fallback covers the rest, the legacy
`"default"` entry is not read as a sink). 123 tests, fmt, clippy clean.

## Output switch no longer stops the stream

Two defects in `retarget_output`, both around the filter-chain rebuild:

- It re-routed the playback streams **unconditionally**, so changing the output
  with the System EQ switch off dragged the user's streams into the EQ — on a
  chain that had just been rebuilt. `RoutingEngine::routed` now records whether
  the streams are routed (as distinct from `current_sink`, which is where the
  chain points), and the re-route is gated on it, matching upstream's
  `restart_engine`.
- With routing on, the streams were left aimed at the sink the rebuild destroys,
  so they pointed at nothing for up to 2 s while the new node appeared. New
  `suspend_routing()` puts them back on their own targets *before* the rebuild,
  keeping the record so the re-route afterwards still knows where each one came
  from. Same order as upstream.

123 tests, fmt, clippy clean. The dropdown itself needs a click from the user to
confirm; the log says which path ran.

## Output switch: move the chain's output live instead of rebuilding

`retarget_output` carried a comment asserting that the chain's output client
cannot be retargeted because it is `node.passive`, so the only way to change
destination was to rebuild the module — and a rebuild destroys `mini_eq_sink`,
which is what was stopping playback.

That assertion was wrong. `node.passive` is a property of the adapter's node, not
of the stream it exposes, and `mini_eq_sink_output` is an ordinary stream node
whose target is ordinary metadata. Upstream moves it live and only falls back to
`restart_engine` when the move raises. Proven here with a temporary probe that
moved the stream and read the value back: `verified=true`.

`retarget_output` now tries the live move first and *verifies* it by reading the
target back (bounded 300 ms). On success nothing is rebuilt and no stream is
touched — the user's streams keep their existing links, which is the point of
the feature. Only a failed move falls back to the rebuild path.

123 tests, fmt, clippy clean.

## Update preset (step 1 of the output-modes plan)

The preset panel has an **Update** action (`document-save-symbolic`, next to `+`)
that overwrites the selected custom preset with the current curve. It is enabled
exactly when the state chip reads `Modified`, refuses built-ins the way rename
and remove do, and uses the same live-state reader as Save, so it works whatever
the curve came from: a linked device, a loaded preset, an AutoEq import. This
retires the "press `+`, then rename the new preset to the same name" workaround.

Implementing it exposed a second defect: **the state chip was only refreshed when
a preset was loaded or selected**, never on edits, so it kept reading `Saved`
while the curve moved away from the preset — and anything gated on it (now the
Update button) would never wake up. The chip is now recomputed from the live
signature in the 33 ms loop, only when the signature actually changes, so the
cost is one payload hash per edit.

123 tests, fmt, clippy clean.

## Follow-default that actually follows (step 2 of the output-modes plan)

The dropdown's index 0 ("Default Output (follow system)") was a label with no
behaviour: the chain's output was fixed when the module loaded, so going back
to the default had to rebuild the module — and the 500 ms watcher that was
supposed to notice the default changing only moved the **monitor**, with a
comment saying the chain re-link was "deliberately NOT attempted". Both halves
of the same lie.

`retarget_output` already had a cheap live-move path, so the watcher's refusal
was stale, not cautious. It now calls `be.retarget_output(&new_default)` when
the default changes and the user has not pinned a device: live move takes →
nothing rebuilt, no stream touched, inaudible; live move fails → the rebuild
path, which hands streams back before the module goes away and re-routes only
if they were routed. After a retarget it also applies the new device's preset
and updates `AppState::output_sink` / `StateChanged`, as the dropdown does; the
monitor follows after, only when it was already following the chain. Gated on
`output_follows_default`, so a pinned device is left alone.

The poll itself was pure waste. `refresh_default_audio_sink_name()` pumped the
PipeWire loop for up to 50 ms per 500 ms tick to catch a metadata property the
`property` listener on the `default` object already delivers in real time — it
was bound already, it just never had a signal. `RoutingEngine` gains
`default_sink_changed: Rc<RefCell<bool>>` set by that listener;
`current_default_audio_sink()` reads the cache without pumping;
`take_default_sink_change()` returns the new sink and clears the flag, or
`None`, so the 500 ms timer is a cheap flag read on the common case and acts on
a change exactly once. `default_audio_sink_name()` keeps its initial-bind pump
and drops the per-tick pump; `refresh_*` is deleted from the public surface and
`pipewire_backend.rs` exposes `take_default_sink_change()`.

123 tests, fmt, clippy clean. Live: the chain retargets on a real default-sink
change via the live path (logged `EQ output moved live to … (no rebuild)`).
Whether the switch is gapless needs an ear — the live move touches no playback
stream, but the destination node's ports still relink.

## Mode split: Selected / Reroute (step 3 of the output-modes plan)

`System-wide EQ` is still a switch — "are streams routed through the EQ at all".
Beside it are two toggle buttons in a linked group, named for what they do to
the streams rather than for a scope:

- **Selected** (default): only streams already aimed at the chosen device are
  routed in. The device you picked is the only thing being processed.
- **Reroute**: every eligible stream is moved in regardless of device. This is
  the explicit opt-out from the foreign-target rule, and it is never the
  default because overriding a stream the user pointed elsewhere is the single
  most surprising thing this app can do.

The mode is read from the buttons at switch-on and persisted, so toggling off
and back on restores the mode rather than always re-routing everything. The
default is Selected, which is also what a missing or version-1 config reads as.

`RoutingEngine::target_in_scope(target_object, sink_serial, mode)` is pure —
it takes the target string rather than a stream, so it is testable without a
live PipeWire connection. Selected: no explicit target → in scope (WirePlumber
is choosing the default, which is the device we picked); the chosen serial → in
scope; any other serial → out. Reroute: everything in scope. The blocklist is
applied before this predicate, so it is only ever asked about a stream that
survived it. The chosen sink is identified by its `object.serial`, which is the
value WirePlumber matches on in `target.object`.

`output-presets.json` is now version 2, carrying `mode` and `monitor`. The
reader tolerates version 1 (missing `mode` → Selected, missing `monitor` →
follow) and drops the legacy `"default"` link key on the next write — that key
is the fallback, never a device, and reading it back as a sink made
`output_preset_for_sink("default")` return a preset. New: `output_routing_mode`
/ `set_output_routing_mode`, `output_monitor_sink` / `set_output_monitor_sink`,
and the `OutputRoutingMode` enum with `from_mode_str` / `as_str`.

D-Bus gains `SetOutputMode` (an `s` argument using the same `selected` /
`reroute` values the UI buttons use), and `output_mode`, `output_preset` and
`monitor_sink` are published in `GetState` alongside the new
`output-mode` / `output-preset` / `monitor-sink` capabilities. `AppState`
publishes these per tick from the window rather than holding stale values, and
`SetOutputMode` mirrors the widget and re-routes when the engine is on, keeping
the two in agreement whichever side moved first.

128 tests, fmt, clippy clean. Live: switching the mode while the engine is on
re-routes immediately (logged `Output mode -> Reroute (re-routed)`); switching
off hands the streams back and disables the A/B switch, which is inert in that
state.

## Curve picker and auto-write-back (step 4 of the output-modes plan)

The "Link to Output" button wrote the sink's node name into a value label that
nothing ever read back, so a device could be "linked" to a preset and the link
would never be applied. The row is now `Curve [ <preset> ▾ ] [unlink]`. Choosing
a preset in the dropdown links it to the active device immediately, so the
reader will use it on the next switch — and it loads that preset onto the curve
now, so what you see is what the device gets. Unlink drops the link and the
fallback applies instead. The model is refilled from the preset library on a
330 ms cadence, so a preset created or deleted elsewhere shows up here without a
restart, and the selection tracks the active device's linked preset.
**Set Fallback** stays as it is: one global preset for devices with no link.

Editing the EQ while a device is linked should not require remembering to press
Update. When the live curve moves away from the preset linked to the active
device, it is written into that preset after a 1.5 s debounce — on the last edit,
not the last tick, so a drag rewrites once after it settles rather than
continuously. It only writes into a preset linked from **exactly one** device:
writing into one linked from two would silently change the curve for a device the
user did not touch, which is worse than leaving it Modified. Built-ins are never
written. The comparison is against the preset's own saved signature
(`output_preset_saved_signature_for_sink`), not the panel's "modified" state, so
the write-back is independent of which preset is selected in the panel.

130 tests, fmt, clippy clean.

## Monitor device (step 5 of the output-modes plan)

The monitor always followed the chain's output, so you could not equalise on
headphones and watch the speakers. The monitor's settings popover now holds a
**Monitor device** dropdown: `Follow EQ output` (index 0, the default) or a
specific sink. The model is refilled from PipeWire on a 330 ms cadence, so a
hotplugged device appears here without a restart. It is listen-only — it does
not change where the EQ'd audio goes, and the tooltip and the status line say
so. `retarget_monitor` was already a live retarget, so this is cheap.

The choice is persisted in `output-presets.json` as `monitor`: `None` for
follow, or the sink's node name. On startup the persisted pin decides the
initial selection, so a pinned monitor survives a restart even before the
dropdown has ever been touched. `resolve_monitor_target` (now on
`PipeWireBackend`) prefers the pin and falls back to the chain's current
output, so a pinned monitor also survives a chain rebuild.
