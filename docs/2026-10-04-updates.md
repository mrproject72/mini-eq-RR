# 2026-10-04 Updates

Gap analysis against upstream `bhack/mini-eq` plus the first fix.
Analysis and prioritised backlog: `docs/PLAN/gap-closure-2026-10-04.md`.

## Headline

The D-Bus remote-control interface — the foundation for the planned GNOME
Shell extension — was **completely non-functional**. Four independent defects
had stacked up. All fixed and verified against a live instance.

## D-Bus remote control: unreachable *and* inert

### 1. The bus name was never claimed

`acquire_bus_name()` existed in `dbus_control.rs` and **had no call sites**.
`MiniEqDBusControl::register()` registered the object on the session
connection but never owned the well-known name, so every remote call failed:

```
$ gdbus call --session --dest io.github.mrproject72.mini_eq_rr \
    --object-path /io/github/mrproject72/mini_eq_rr/Control \
    --method io.github.mrproject72.MiniEqRR.Control.GetState
Error: ...ServiceUnknown: The name io.github.mrproject72.mini_eq_rr was not
provided by any .service files
```

`register()` now claims the name itself. `MiniEqDBusControl` keeps the owner
id in a new `bus_owner_id` field — **dropping that id releases the name**, so
it has to be retained.

### 2. The handler was not connected to the window

`AppState` was the only `MiniEqAppHandler` impl and lived in `main.rs`, so
`window.rs` could not reach it (it had zero references). Six methods were
empty or constant:

```rust
fn analyzer_levels(&self) -> Vec<f64> { Vec::new() }
fn analyzer_display_gain_db(&self) -> f64 { 0.0 }
fn ui_shutting_down(&self) -> bool { false }
fn present_main_window(&self, _) {}
fn quit_fully(&self) {}
fn load_library_preset(&self, _) {}
```

The `Mutex<bool>` fields were written only by D-Bus callers and read only by
`build_state`, so `GetState` reported `eq_enabled = true` forever.

**Fix:** moved `AppState` into the library as `src/remote_control.rs`. The
window now owns the truth and pushes changes back into `AppState`.

### 3. Why a command queue rather than calling GTK directly

`MiniEqAppHandler` is bounded by `Send + Sync` because the `gio` vtable
closure that dispatches method calls requires it. GTK objects are
main-thread-only and cannot cross that boundary.

So handlers update the cached state (so `GetState` answers correctly and
immediately) and **post** a `RemoteCommand`. The 33 ms tick drains the queue
and applies it to the real widgets and the PipeWire backend:

```rust
pub enum RemoteCommand {
    SetEqEnabled(bool),
    SetRouting(bool),
    SetPreset(String),
    PresentWindow,
    Quit,
}
```

**The drain sits at the very top of the tick, before `bands` is computed.**
That ordering matters: a preset loaded over D-Bus is therefore already applied
when the tick builds the band snapshot, so the backend push at the end of the
same tick carries the new coefficients. Draining later would apply the preset
but push the *previous* bands.

### 4. Argument extraction was wrong (latent behind #1)

```rust
if let Some(enabled) = params.get::<bool>() {   // always None
```

`params` is the whole argument **tuple**, so a one-argument method arrives as
`(b)`, never a bare `b`. Every setter answered `InvalidArguments`. Fixed to
`params.get::<(bool,)>()` / `::<(String,)>()`. Note `Variant::get` returns
`Option`, not `Result`, in glib 0.22.

This never showed up because nothing could reach the service.

### 5. Both array builders were type-wrong and **panicked the process**

```rust
glib::Variant::array_from_iter::<glib::Variant>(levels.iter().map(|l| ...))
```

Infers the element type from `Variant`'s own static type instead of `d`, then
trips `assertion failed: value.is_type(type_)` inside glib. Because it fires
from the GLib tick trampoline (`panic in a function that cannot unwind`), the
whole process aborted. Fixed with the explicit element type:

```rust
glib::Variant::array_from_iter_with_type(
    glib::VariantTy::DOUBLE,
    levels.iter().copied().map(glib::Variant::from),
)
```

Same bug in `ListPresets` (`as`).

## A/B compare switch was a dead widget

`utility.bypass_switch` was constructed and added to the graph header with
**no handler**, while `update_state_live_or_reload` hardcoded
`eq_enabled = true` — so bands were always pushed wet and comparing with/without
the EQ did nothing.

- `update_state_live_or_reload` now takes `eq_enabled`.
- The tick folds the bypass state into the push signature (appending `'0'`/`'1'`)
  so toggling it counts as a change and triggers a push.
- The switch got a `state-set` handler mirroring state into `AppState`.
- `build_state`'s hardcoded `running: false` replaced with a real `running()`
  (upstream: `controller is not None`).

## A `RefCell` panic while syncing the preset name

First attempt read `presets.borrow().current_preset_name()` from inside the
panel's apply callback. That callback runs *while* `load_library_preset` holds
`presets.borrow_mut()`, so it panicked with `RefCell already mutably borrowed`
and killed the app.

Fixed by syncing in one place in the tick, immediately after the drain — which
also covers both the UI row selection and the D-Bus command, instead of two
call sites that can disagree.

## `AnalyzerLevelsChanged`: value-gating starves the signal

First implementation emitted only when the level vector differed from the last
publish. Silence and steady tones produce an **identical spectrum every frame**,
so the signal never fired at all — verified: 0 emissions in 3 s.

Now time-throttled at 100 ms, matching upstream
`CONTROL_ANALYZER_EMIT_INTERVAL_SECONDS = 0.10`. Measured ~8-10 emissions/s.

## Follow-up: A/B compare and analyzer labels (user-reported)

Two issues reported after the D-Bus work:

### A/B compare was inaudible

**Cause:** the bypass state was folded into the push signature correctly, but
the push was still gated behind `last_push.elapsed() >= 400ms` — a debounce
that exists so *fader drags* don't thrash the DSP. A deliberate A/B toggle
therefore took up to 400 ms, and toggling back inside that window cancelled it,
so the switch could produce no change at all.

**Fix:** the debounce now guards only band/preamp edits. A bypass change pushes
on the next tick. Measured: applied within 200 ms.

**Verified the DSP side rather than assuming it.** `bq_raw_control_values` with
`eq_enabled=false` collapses every band node to unity gain (b0 == a0, b1/b2/a1/a2
all 0) and differs from the active set — identical to upstream
`filter_chain.py` formula-for-formula. Pinned by
`test_eq_bypass_pushes_flat_response_not_the_active_curve`.

**Testing note:** bypass is only audible when the curve is non-flat. On a flat
curve there is correctly nothing to hear.

### Analyzer controls were unlabelled

Two sliders and a switch sat in one horizontal box with only tooltips. Replaced
with three labelled rows ("Smoothing" + `NN%`, "Display Gain" + `+N dB`,
"Freeze") in a `boxed-list`, mirroring upstream's `Adw.ActionRow` layout.

### Gotcha found while testing this

`biquad_node_name` formats as `band_{side}_{index}` → `band_l_0`, **not**
`band_0_l`. Easy to get backwards when writing assertions.

Also note: measuring an EQ bypass via the analyzer is unreliable — it is a
monitor tap on live program material, so samples taken seconds apart are not
comparable. Use a unit test for the DSP and your ears for the UX.

100 tests pass; fmt and clippy clean.

## Follow-up 2: A/B bypass verified with a controlled signal

The second "A/B switch does nothing" report turned out to be a **measurement
problem, not a code problem** — but verifying it properly required a
controlled source, and it exposed a repeatable way to test DSP changes.

Measuring an EQ bypass from the analyzer while ordinary program material plays
is meaningless: samples taken seconds apart differ by more than the effect being
measured. Early "before/after" comparisons here were pure noise.

**Controlled method that works:** play a known sine through the EQ and compare
the captured spectrum.

```bash
# 125 Hz tone at -12 dBFS
python3 -c "
import numpy as np, wave
sr=48000; t=np.linspace(0,10,sr*10,endpoint=False)
w=wave.open('/tmp/tone.wav','w'); w.setnchannels(1); w.setsampwidth(2); w.setframerate(sr)
w.writeframes((0.3*np.sin(2*np.pi*125*t)*32767).astype('<i2').tobytes()); w.close()"

# route everything through the EQ, load a +18 dB @ 125 Hz preset, then:
#   paplay /tmp/tone.wav          while capturing AnalyzerLevelsChanged -> EQ ON
#   SetEqEnabled false            then capture again                  -> BYPASSED
```

Result on the current build (median of captured frames):

| state | peak bin | level |
|---|---|---|
| EQ on (+18 dB @ 125 Hz) | 2 | 0.614 |
| bypassed | 3 | 0.268 |

**+7.2 dB** with the EQ engaged. The bypass is unambiguously working.

An earlier flat-vs-boosted preset comparison (also live-push only, no module
reload) showed only ~2 dB, which looked like proof the push was broken — that
reading was also just program-material noise, not a real result.

**Lesson recorded:** never conclude a DSP change is broken from analyzer
levels captured without a controlled source. Use a test tone, or a unit test
for the coefficient maths.

### Observability added

`A/B compare: bypassed=<bool> (eq_enabled=<bool>)` now logs at INFO on every
toggle, and each backend push logs `eq_enabled` at DEBUG. The switch previously
gave no feedback at all, which is why three reports of "it does nothing" were
impossible to diagnose from the outside.

## Follow-up 3: the actual cause — A/B is inert unless routing is on

Third "A/B does nothing" report came with a log showing the toggle reaching the
push path correctly:

```
A/B compare: bypassed=true (eq_enabled=false)
Preamp gain set to 0 dB
```

`GetState` at that moment: **`routed: false`**.

**Root cause: architectural, not a bug in the bypass logic.** The A/B switch
bypasses the EQ *inside* `mini_eq_sink`'s filter chain. While systemwide routing
is off, playback streams are sent straight to the real sink and never touch
`mini_eq_sink`, so every EQ control — including A/B — is out of the signal path.
This matches upstream: upstream's bypass also only re-passes the filter graph
inside the same sink.

So the earlier controlled measurement (+7.2 dB) was valid precisely because
routing had been switched on before it.

**To hear A/B: enable the systemwide EQ switch first.**

### UX fix

The switch looked and behaved like a live control while having no effect, which
is what made three reports undiagnosable. It is now insensitive while routing
is off, with a tooltip that says why, and re-enabled with an explanatory tooltip
when routing goes on. Seeded from the routing switch's real state on startup
because `state-set` does not fire for an initial state.

`set_sensitive(false)` only blocks user interaction, so the D-Bus
`SetEqEnabled` path still works programmatically.

## Follow-up 4: root cause — every live DSP push is silently ignored

The user was right and I was wrong three times. The A/B switch was never the
problem: **the entire live EQ update path does nothing.** See
`docs/BUGS.md` → P0.

### Evidence (clean, controlled, single tone, zero background)

Noise floor measured at exactly 0.000 in every bin, so this is not confounded:

| preset state (1 kHz tone, routed through the EQ) | peak bin | level |
|---|---|---|
| Bell **+18 dB** @ 1 kHz, EQ on | 5 | 0.6461 |
| Bell +18 dB @ 1 kHz, bypassed | 5 | 0.6461 |
| Bell **−18 dB** @ 1 kHz, EQ on | 5 | 0.6461 |

A 36 dB swing, bit-identical output. `apply_live_controls` logs
"pushed 132 control(s)" and PipeWire accepts the pod without error while
discarding every control.

Cause: the pod is built as an **untyped struct of alternating (string, double)**
inside the props object. Upstream sends a **dict** (`GLib.Variant("a{sd}", …)` →
`Param.new_props_controls`, serialised by `spa_pod_from_variant` as
`SPA_TYPE_OBJECT_Dict`). filter-graph's `parse_params` expects the dict form and
silently drops the struct form.

Because `default_bands()` is 10 Bells at 0 dB, the module is loaded flat and
never changes — so band, preamp, type, solo/mute edits **and** A/B are all
dead. Only the routing switch has any audible effect, which matches every
report received.

### My measurement mistakes, recorded so they are not repeated

1. **Compared analyzer levels seconds apart while music played.** Noise swamped
   the effect; produced one false "+7.2 dB works" and one false "2 dB = broken".
2. **Wrote test presets with `"preamp"` instead of `preamp_db`** — silently
   ignored, so every test preset loaded at 0 dB preamp.
3. **Wrote `"filter_type": 0` believing it was a Bell. `0` is `Off`** (Bell is
   `1`), so the first "proof that bypass does nothing" was measuring two flat
   curves. The `+18`/`−18` comparison above only became meaningful once the
   fixture was actually a Bell — and it then showed the real bug.

The general lesson: when a DSP change appears to do nothing, first prove the
*fixture* is doing something, and measure against a controlled source. A
measurement that shows literally zero difference almost always means the test
setup is inert, not that the feature is broken.

### Status

**Not fixed.** Recorded as P0. The bypass work from earlier in this session is
correct but was fixing a non-bug; it stays (the debounce and observability
changes are still right), however the switch remains inaudible until the pod
encoding is corrected.

## Follow-up 5: my P0 "fix" was wrong — reverted

I claimed the pod needed `SPA_POD_PROP_FLAG_HINT_DICT` and a leading
`Int: n_items`, inferred from upstream's `GLib.Variant("a{sd}", …)`. I applied
it. **It made things worse**: the user reported the EQ became completely
ineffective with systemwide routing on.

That regression was itself the useful evidence. I pulled the PipeWire source
(`git clone --depth 1 --filter=blob:none --sparse
https://github.com/PipeWire/pipewire.git`) and read the actual parser.

`spa/include/spa/param/props.h`:

```c
SPA_PROP_START_Other = 0x80000,
SPA_PROP_params,   /**< simple control params
                    *    (Struct(
                    *      (String : key,
                    *       Pod    : value)*)) */
```

`spa/plugins/filter-graph/filter-graph.c:parse_params()`:

```c
spa_pod_parser_push_struct(&prs, &f);
while (true) {
        if (spa_pod_parser_get_string(&prs, &name) < 0)
                break;              /* <-- bails on the first non-string */
        ...
        set_control_value(def_node, name, val);
}
```

So:

- `SPA_PROP_params == 0x80001` — the key we already used was right.
- The payload is a **bare `Struct((String, Pod)*)`** — no count, no dict flag.
- The loop **`break`s on the first field it cannot read as a string**, so my
  leading `Int: n_items` aborted the parse at field zero and every control was
  dropped. Exactly the reported symptom.
- `find_port()` splits `node:control` on `:` and resolves the node by name across
  the whole graph, so `band_l_0:b0` is correct.

**The original encoding was already correct. Reverted.**

Two tests now pin the real format (`props_pod_is_a_bare_struct_of_string_value_pairs`,
`props_pod_carries_every_control_name`), including an assertion that the payload
*starts with a string*, so the bad shape cannot come back silently.

## Follow-up 7: Gap 2 — AutoEq import made reachable (three defects)

The original gap analysis understated this badly. It claimed
`window_autoeq.rs` was "a 3-function shell" needing "search entry + debounce +
results list, preview drawing, import wiring". That was wrong: I had counted
only top-level `fn`s and missed everything built inside `new()`. The dialog
already had a search entry, a results list and a full curve preview. The real
gaps were narrower and harder.

### What was actually broken

1. **Nothing constructed the dialog.** No call site anywhere. Now opened from a
   new AutoEq button in the Presets toolbar via `set_autoeq_callback`.

2. **The HTTP path aborted the process.** `autoeq.rs` used `reqwest`'s async
   client inside `glib::MainContext::spawn_local`. reqwest needs a Tokio reactor
   and the app has no Tokio runtime, so the first call panicked with
   *"there is no reactor running, must be called from the context of a Tokio 1.x
   runtime"* — and from the GLib tick trampoline it could not unwind, so the
   whole process died. This had never fired only because the dialog was
   unreachable.

   Fixed by converting both HTTP calls to `reqwest::blocking` (added the
   `blocking` feature) and running them on a worker thread. GTK objects are not
   `Send`, so only the plain result crosses threads via a channel, and widgets
   are updated from a `spawn_local` continuation.

3. **Cache written to the wrong directory.** Passed `core::user_config_dir()`
   (`~/.config`) where the loader appends `autoeq/entries.json` itself, so the
   index landed in `~/.config/autoeq/` instead of `~/.config/mini-eq/autoeq/`.
   Now uses `core::app_config_dir()`. This also corrects a stale line in
   `AGENTS.md` that claimed the cache lived under `~/.cache/mini-eq/autoeq/`.

4. **Import was a `println!` stub.** Now saves the profile as a preset and loads
   it, via `unique_preset_name()` so a repeat import cannot silently overwrite an
   earlier one — AutoEq names repeat across measurement sources.

5. **Index only loaded on refresh.** The first search always reported "No
   results found" until the user happened to press refresh. It now loads when the
   dialog opens, with one shared code path for both.

### Verification

Probed end-to-end by temporarily firing the button handler at startup (probe
removed afterwards): dialog opens, no panic, index downloads and caches
**6033 headphone names / 8850 measurement entries**.

Two new tests use the real `https://autoeq.app/entries` payload shape —
`test_parse_entries_real_api_shape` and
`test_parse_entries_rejects_malformed_json`.

### Correction to the record

`format_autoeq_parametric_eq` **does** exist (private). I earlier reported it
missing because I grepped only for `pub fn`. The conversion to APO text is
already implemented and is what feeds `parse_apo_file`.

## Follow-up 8: Gap 3 — single-instance guard

`instance.rs` held an `InstanceGuard` that was an in-process
`Arc<Mutex<bool>>` and was **never instantiated**. It could not have prevented a
second instance even if it had been. Replaced with a real exclusive `flock` on
`$XDG_RUNTIME_DIR/mini-eq-rr.lock` (falling back to a uid-scoped temp dir, like
upstream). Uses `nix::fcntl::Flock` with `LockExclusiveNonblock`; `nix` was
already a direct dependency, so no new crate.

Acquired in `main()` **after** the one-shot subcommands and `--check-deps`, so
those keep working while the app is open.

### The reaping half of the plan was wrong, and was dropped

The plan called for upstream's orphaned-filter-chain reaping. Before
implementing it I tested the premise: `kill -9` a running instance and watch
PipeWire.

Result: `mini_eq_sink` and `mini_eq_sink_output` are **both gone within a few
seconds**. The reason is architectural — this port calls
`pw_context_load_module`, so the filter chain lives in the PipeWire *daemon* and
is owned by our client connection; the daemon drops it on disconnect. Upstream
needs the `/proc` scanner only because the Python app spawns `pipewire -c ...`
as a **child process**, which a crash can orphan.

So the scanner was not implemented. A routine that walks `/proc` and sends
`SIGTERM`/`SIGKILL` to process groups would be a liability with no benefit here.

### Verified live

| scenario | result |
|---|---|
| second instance while one runs | refused, `mini-eq RR is already running (pid 427227).`, exit 1 |
| only one process afterwards | yes (`pgrep -xc` = 1) |
| restart after `kill -9` | starts cleanly — kernel dropped the lock |
| restart after `SIGTERM` | starts cleanly |
| `--check-deps` while running | works, exit 0 |

### Test isolation

The first version of the tests used the real lock file and failed whenever the
app happened to be running — precisely when they are least useful. Split
`try_acquire_at(path)` / `is_lock_held_at(path)` out so the tests use a private
temp lock file. Verified: 108 tests pass with an instance running.

Suite: 108 tests. fmt and clippy clean.
